# Plan 2.5.12 - Restauracion, tiempo local, API y corte

## Base y retorno

- Base funcional: `v2.5.11`.
- Los tags `v2.5.5` a `v2.5.11` se conservan sin reescritura ni eliminación.
- El código no se tocará fuera de los puntos anotados a continuación. Si una corrección exige cambiar ventas, permisos, inventario o un flujo no citado, se explicará primero y se pedirá aprobación.

## Hallazgos que atiende

- Restaurar no recupera de forma confiable cortes y reportes después de limpiar datos, probablemente porque sus consultas agrupan fechas usando UTC (`+00:00`) en lugar del día operativo local.
- La hora de negocio debe tomar la zona configurada en Windows. En el equipo de prueba es `-06:00`; no se debe fijar ese valor, porque Windows puede cambiar por horario de verano o por otra región.
- Si la API cae durante el uso, falta una advertencia visible en cualquier parte de JetVenta y otra cuando la API vuelve a responder, ya sea porque el usuario la levantó o porque se recuperó sola.
- Diagnóstico debe describir correctamente la cola técnica y no presentar números confusos.
- El corte de cajero necesita un comprobante completo por turno; el corte del día debe distinguirse del efectivo pendiente del turno.
- El límite de efectivo debe considerar solamente efectivo: fondo, ventas en efectivo, entradas, salidas y ajustes de efectivo. No debe sumar tarjeta, transferencia ni crédito.
- La nota solicita elegir entre advertir en cada venta o bloquear temporalmente ventas al superar el límite.

## Bloque A - Restauracion y conservacion de datos

1. Revisar el resultado de restaurar y limpiar datos en una base de prueba, específicamente cortes, ventas, movimientos, reportes derivados y metadatos del respaldo.
2. Mantener la secuencia existente: validar checksum, crear copia preventiva, detener API, restaurar, validar la base restaurada y reiniciar API.
3. Corregir sólo el paso que impida que los datos de corte y reporte restaurados sean consultables; no modificar la estructura de ventas ni el formato de respaldos sin evidencia de que sea necesario.
4. Mostrar progreso y resultado final entendibles, indicando la ruta de diagnóstico cuando falle.

**Justificación:** las notas reportan restauración aparentemente terminada, pero cortes y reportes incompletos. Una restauración no es válida si recupera tablas sin recuperar la información operativa que depende de ellas.

## Bloque B - Zona horaria y fechas mostradas

1. Tomar la zona horaria local de Windows como zona operativa del negocio, sin fijar manualmente `-06:00`.
2. Conservar UTC en la base para integridad, pero convertir a zona local al mostrar, imprimir o exportar fechas.
3. Para cortes y reportes por fecha, construir inicio y fin del día en la zona de Windows y convertir esos límites a UTC antes de consultar la base.
4. No recalcular ni migrar timestamps históricos sin aprobación: se corregirá la interpretación de salida y de los periodos de consulta, no el dato original.

**Justificación:** la diferencia de seis horas anotada coincide con UTC frente a la zona de México. Los respaldos restauran registros, pero los cortes y reportes pueden quedar fuera del día consultado si sus límites se calculan en `+00:00`. Cambiar almacenamiento global sería riesgoso; corregir la zona de presentación y de consulta es acotado y reversible.

## Bloque C - API y diagnostico

1. Centralizar una comprobación liviana de disponibilidad de API mientras JetVenta está abierto, independientemente de la sección o diálogo que el usuario tenga abierto.
2. Mostrar una alerta roja visible cuando se pierde conexión, con instrucción de ir a Configuración > Diagnóstico > Levantar API.
3. Mostrar una alerta azul una sola vez cuando la API vuelva a responder, tanto si JetVenta detecta que se levantó sola como si se reparó desde Diagnóstico.
4. En Diagnóstico, explicar qué son documentos técnicos en cola, separar pendientes reales de residuos y permitir limpiar sólo residuos confirmados sin afectar ventas.

**Justificación:** las notas exigen que un usuario común pueda identificar una caída de API y recuperar la operación sin comandos ni operaciones inciertas.

## Bloque D - Corte y limite de efectivo

1. Corregir el cálculo del límite para usar exclusivamente movimientos de efectivo. Se excluirán tarjeta, transferencia, crédito y cualquier pago no efectivo.
2. Agregar a Configuración > Corte una decisión explícita: sólo advertir en cada venta o bloquear ventas hasta bajar efectivo mediante retiro autorizado.
3. Mantener la alerta existente de límite y hacer explícito que se refiere a efectivo esperado en caja.
4. Revisar el comprobante de corte de cajero para que incluya fondo inicial, ventas por forma de pago, entradas, salidas, efectivo esperado, efectivo contado, diferencia y datos del turno/cajero.
5. Distinguir en texto y cálculo el corte del turno actual del corte del día por fecha.

**Justificación:** mezclar pagos electrónicos o crédito con efectivo provoca retiros innecesarios y cortes incorrectos. El cajero necesita saber si sólo debe avisar o detener ventas antes de exceder el límite.

## Pruebas de regresion obligatorias

1. Crear respaldo, limpiar datos, restaurar y comprobar venta, corte, movimiento y reporte de prueba.
2. Comparar fecha/hora de Windows con respaldo, corte y reporte en la misma máquina.
3. Finalizar la API mientras JetVenta está abierto, observar alerta roja, levantar API desde Diagnóstico y observar alerta azul.
4. Probar diagnóstico con documentos técnicos residuales y confirmar que limpiar no borra ventas ni tickets.
5. Cobrar efectivo, tarjeta, transferencia y crédito; confirmar que sólo el efectivo altera el límite.
6. Probar modo advertencia y modo bloqueo de límite de efectivo.
7. Generar corte de cajero y corte del día; comprobar periodo, cajero, pagos y movimientos.

## Fuera de alcance

- No se cambian permisos, ventas, catálogo, importación/exportación, dispositivos, licencia, multicaja ni integración de terminales.
- No se cambia el formato de respaldos ni se migran datos históricos salvo que la revisión del fallo de restauración demuestre que es imprescindible; en ese caso se solicitará aprobación antes.
